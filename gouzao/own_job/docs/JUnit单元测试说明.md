# JUnit 单元测试说明

## AI 辅助课堂同伴互评工具（Java 桌面版）

---

## 摘要

本文档说明《AI 辅助课堂同伴互评工具》的测试设计与全部 50 个 JUnit 5 用例。内容包括测试环境、运行方式、
测试替身的选择依据、每个用例的输入与断言、执行结果、JaCoCo 覆盖率实测数据，以及测试发现的 5 个真实缺陷。
文档面向两类读者：需要复核测试是否充分的评阅人，以及需要在项目上继续添加用例的开发者。

**关键词：** JUnit 5；单元测试；集成测试；测试替身；覆盖率；JaCoCo

## 1 测试范围与目标

| 项 | 内容 |
| --- | --- |
| 被测系统 | AI 辅助课堂同伴互评工具（Java 17 + Swing + JDBC） |
| 测试范围 | 业务规则（计分/分配/校验/注册）、数据访问、端到端业务链、AI 协议层、配置定位 |
| 不在范围 | Swing 界面交互（用离屏截图 + 人工比对替代）、真实 DeepSeek 服务（用本地桩服务替代） |
| 用例总数 | 50 个，7 个测试类 |
| 当前结果 | 50 通过 / 0 失败 / 0 错误 / 0 跳过 |
| 覆盖情况 | 非界面包行覆盖 71.9%，关键策略类 90% 以上（JaCoCo 0.8.12 实测） |

测试目标不是「跑通就行」，而是三条可检验的命题：

1. **业务规则在边界处仍然正确**：权重不足 100、区间跨度为 0、评审人数超过提交数、字数刚好等于下限；
2. **失败路径给得出确定的反应**：非法输入必须抛 `ValidationException` 并带可读原因，而不是返回 null 或吞掉；
3. **跨层协作不依赖界面**：整条业务链能在内存数据库上跑完，说明业务逻辑没有偷偷依赖 Swing 或真实 MySQL。

## 2 测试环境

| 项 | 版本/说明 |
| --- | --- |
| JDK | 17（`maven.compiler.release=17`） |
| 构建 | Maven 3.9.x |
| 测试框架 | JUnit 5（junit-jupiter 5.10.2） |
| 断言 | `org.junit.jupiter.api.Assertions` 静态导入，无第三方断言库 |
| 覆盖率 | JaCoCo Maven Plugin 0.8.12 |
| 测试数据库 | H2 2.2.224，内存模式 `jdbc:h2:mem:...;MODE=MySQL;DATABASE_TO_LOWER=TRUE;DB_CLOSE_DELAY=-1` |
| HTTP 桩 | JDK 自带 `com.sun.net.httpserver.HttpServer`，随机端口 |
| 外部依赖 | 无。测试不访问网络、不写项目目录、不需要 MySQL |
| 编码 | UTF-8（`MAVEN_OPTS=-Dfile.encoding=UTF-8`，Windows 控制台需要） |

关于「为什么不用 Mockito」：项目只依赖 4 个运行期库 + JUnit，没有引入 mock 框架。
`AuthServiceTest` 需要的是一个「记录插入、能按用户名查」的 `UserDao`，手写 30 行内存实现比引入一个框架更轻，
而且内存实现本身就是一份可读的「DAO 契约说明」。这个选择也顺带证明了 `AuthService` 只依赖接口。

## 3 如何运行

### 3.1 命令行

```bash
# 全部用例（约 4 秒）
mvn test

# 单个测试类
mvn test -Dtest=ScoreCalculatorTest

# 单个用例
mvn test -Dtest=ScoreCalculatorTest#zeroSpanIsSafe

# 测试 + 覆盖率报告（生成 target/site/jacoco/index.html）
mvn org.jacoco:jacoco-maven-plugin:0.8.12:prepare-agent test org.jacoco:jacoco-maven-plugin:0.8.12:report
```

Windows 下如果控制台中文乱码，先设置：

```bat
set MAVEN_OPTS=-Dfile.encoding=UTF-8
```

### 3.2 在 IDE 中运行

IDEA / Eclipse 直接右键测试类或方法运行即可，无需额外配置：所有测试都不依赖外部资源路径，
`WorkflowIntegrationTest` 使用内存库，`AiSuggestionProviderTest` 使用进程内 HTTP 桩。

### 3.3 结果查看

| 位置 | 内容 |
| --- | --- |
| 控制台 | `Tests run: 50, Failures: 0, Errors: 0, Skipped: 0` |
| `target/surefire-reports/*.txt` | 每个测试类的用例数、耗时 |
| `target/surefire-reports/*.xml` | 机器可读结果，便于 CI 集成 |
| `target/site/jacoco/index.html` | 覆盖率报告（行/分支/方法/类） |

## 4 测试设计

### 4.1 分层策略与测试替身

| 层次 | 测试类 | 依赖的真实组件 | 测试替身 | 关心什么 |
| --- | --- | --- | --- | --- |
| 单元 | `ScoreCalculatorTest` | 无 | 无（纯对象） | 算法在边界上的数值正确性 |
| 单元 | `RandomRingAllocatorTest` | 无 | 固定种子 `Random(42)` | 分配结果的集合性质 |
| 单元 | `RubricValidatorTest` | 无 | 无 | 校验规则与提示文案 |
| 单元 | `AppHomeTest` | 文件系统（临时目录） | 系统属性 | 路径推导的优先级 |
| 服务 | `AuthServiceTest` | 无 | 手写内存 `UserDao` | 规则顺序与失败提示 |
| 集成 | `WorkflowIntegrationTest` | H2 内存库 + 全部 DAO/服务 | 内存库本身即替身 | 跨层协作与事务 |
| 协议 | `AiSuggestionProviderTest` | JDK `HttpClient` | 本地 `HttpServer` 桩 | 请求体、响应解析、错误翻译 |

**替身选择的依据**：能用纯对象就不引入数据库，能用内存实现就不引入 mock 框架，能用本地桩就不联网。
这样测试跑得快（全量 4 秒）、可重复（无网络、无时间依赖）、失败原因明确（不需要区分「是我错了还是环境错了」）。

### 4.2 等价类与边界值

下表是测试用例设计的依据，每个边界都对应至少一个用例：

| 被测项 | 有效等价类 | 无效等价类 | 边界值 |
| --- | --- | --- | --- |
| 提交正文字数 | 20 ~ 20000 | 空、仅空格、19 字、20001 字 | 20、20000 |
| 评语字数 | 10 ~ 2000 | 0 ~ 9 字、2001 字 | 10、2000 |
| 权重合计 | 100 | 99、101、0 | 100 |
| 分值区间 | min < max | min = max、min > max | min = max（跨度 0） |
| 每份评审人数 N | 1 ≤ N ≤ 提交数-1 | N = 0、N = 提交数、N > 提交数-1 | N = 提交数-1 |
| 提交数 | ≥ 2 | 0、1 | 2 |
| 账号格式 | 4~20 位字母数字下划线 | 3 位、含中文、含空格、21 位 | 4、20 |
| 口令长度 | 6 ~ 32 | 5 位、33 位、全空白、等于账号 | 6、32 |
| 模型给出的分数 | 落在区间且为 0.5 倍数 | 999、-20、4.3 | 区间端点 |
| 模型给出的维度名 | 与细则一致 | 编造、带后缀、带围栏 | — |

### 4.3 白盒覆盖目标

写测试前先列出每个被测方法的分支，确保每个分支都有用例走到：

| 被测方法 | 分支 | 对应用例 |

| `AppHome.root` | 有系统属性 / 属性空白 / 有 pom.xml / 无 pom.xml | 4 个用例 |

## 5 测试类详解

### 5.1 ScoreCalculatorTest（5 例，单元）

**被测对象**：`NormalizedWeightedCalculator`、`RawWeightedCalculator`、`ScoreCalculators.of(mode)`。
**被测规则**：总分公式与边界处理。

| 用例 | 输入与操作 | 预期与断言 | 覆盖点 |
| --- | --- | --- | --- |
| 归一化：满分/最低分/中间分 | 细则「完整性 60% [0,10]」「规范性 40% [0,5]」；分数 (10,5)、(0,0)、(5,2.5)、(10,0) | 总分分别为 100、0、50、60（误差 1e-6） | 归一化主路径与端点 |
| 归一化：不同区间混合 | 「完整性 50% [0,10]」「规范性 50% [2,6]」；分数 (5,4) | 总分 50（两个维度都恰好在区间中点） | 区间基准不为 0 的情况 |
| 直接加权 | 「完整性 70% [0,100]」「规范性 30% [0,100]」；分数 (80,80)、(80,0) | 总分分别为 80、56 | `RawWeightedCalculator` |
| 异常输入 | 空细则；分数 99（区间上限 10）；分数 -5 | 返回 0；裁剪为 100；裁剪为 0 | `items.isEmpty()`、`normalize` 的上下裁剪 |
| 区间跨度为 0 | 单维度「固定分 100% [5,5]」，分数 5 | 返回 100，不抛异常 | `span <= 0` 分支（防除零） |

**设计说明**：第一个用例刻意用 60/40 的不对称权重，因为对称权重（50/50）掩盖「权重相乘写错」的缺陷——
如果代码漏乘权重，50/50 下总分仍是 50，测试会误判为通过。第三个用例把 `(80, 0)` 也算进去，
是为了验证「总分不是平均分」，而是真正的加权求和。

### 5.2 RandomRingAllocatorTest（5 例，单元）

**被测对象**：`RandomRingAllocator.allocate(assignmentId, submissions, perSubmission, random)`。
**被测性质**：分配结果必须满足四个不变量——数量正确、不自评、不重复、工作量均衡。

| 用例 | 输入与操作 | 预期与断言 | 覆盖点 |
| --- | --- | --- | --- |
| 任务数正确 | 10 份提交，N = 3 | 任务总数 30；每份提交恰好 3 名评审人 | 主路径与数量不变量 |
| 不自评且不重复 | 同上，遍历全部任务 | 每条任务 `reviewerId != authorId`；`(submissionId, reviewerId)` 集合无重复 | 环状顺延的两个性质 |
| 工作量均衡 | 9 名学生全部提交，N = 2 | 每名评审人恰好 2 条任务（去重后值为 `{2L}`） | 公平性 |
| 可复现 | 同一 `Random(42)` 种子生成两次结果 | 两次的 submissionId 与 reviewerId 序列完全一致 | 随机源可注入 |
| 参数边界 | 提交数 6，N = 2 → 允许；N = 3 → 拒绝；提交数 1 → 拒绝；N = 0 → 拒绝 | 允许时返回 6 条；其余三种抛 `ValidationException` | 参数校验的三个分支 |

**设计说明**：这里没有断言「具体分配给了谁」，因为那是实现细节，换个随机源就变。
断言的是**不变量**（性质），这才是算法契约。可复现用例是为了让失败可排查——
随机测试如果没有固定种子，失败后无法重现，等于没有测试。

### 5.3 RubricValidatorTest（4 例，单元）

**被测对象**：`RubricValidator`。
**被测规则**：权重合计必须 100、条数 1~12、维度名唯一、min < max。

| 用例 | 输入与操作 | 预期与断言 | 覆盖点 |
| --- | --- | --- | --- |
| 合法细则通过 | 三条细则，权重 40/30/30 | 不抛异常 | 主路径 |
| 权重合计不为 100 | 40/30/20（合计 90）；40/40/40（合计 120） | 抛 `ValidationException`，消息含「90」「100」 | 权重校验与提示可读性 |
| 空细则 / 重名 / 非法区间 | 空列表；两条同名；范围 [8,2]；范围 [0,0] | 分别抛出，消息分别指出「至少」/「重复」/「下限」 | 三个独立分支 |
| 合计计算与格式化 | 40/30/30；33.3 × 3 | `totalWeight()` 返回 100 与 99.9；格式化输出带 `%` | 数值计算与展示 |

**设计说明**：第三、四组把多个非法输入放在同一个用例里，是因为它们**断言的是同一个行为**（拒绝并给出原因），
拆成多个方法只会增加维护成本。判断标准是「失败时的定位信息是否足够」——如果一条断言失败就能指出问题，就不用拆。

### 5.4 AuthServiceTest（13 例，服务）

**被测对象**：`AuthService.register(RegistrationRequest)` 与 `login`。
**测试替身**：`InMemoryUserDao`（30 行，实现 `existsByUsername` / `insert` / `findByUsername`，插入时回填自增 id）。

| 用例 | 输入与操作 | 预期与断言 | 覆盖点 |
| --- | --- | --- | --- |
| 学生注册成功 | `2023901 / 张同学 / abc123` | 返回用户 id > 0（主键回填）；角色 `STUDENT`；`password_hash` 不等于明文 | 主路径与摘要存储 |
| 注册后可登录 | 同上，再 `login(2023901, abc123)` | 登录成功，姓名与角色一致 | 注册与登录的口令一致性 |
| 账号重复 | 注册两次同一账号 | 第二次抛 `ValidationException`，消息含「已被注册」 | 查重分支 |
| 两次口令不一致 | `abc123` / `abc124` | 抛出，消息含「不一致」 | 口令校验 |
| 口令短于 6 位 | `abc12` | 抛出，消息含「6」 | 长度下限 |
| 口令与账号相同 | `abc123 / abc123` | 抛出，消息含「不能与账号相同」 | 弱口令规则 |
| 全空白口令 | `"   "` | 抛出（先被 trim 判定为空） | 空白处理 |
| 账号格式非法 | `abc`（3 位）、`张三abc123`（含中文）、`abc 123`（含空格） | 三次分别抛出，且内存 DAO 中查不到该账号 | 正则 `[A-Za-z0-9_]{4,20}` |
| 姓名为空 | 姓名 `"  "` | 抛出，消息含「姓名」 | 必填校验 |
| 教师邀请码 | 邀请码配置 `TEACH2026`；先错后对 | 错误抛「邀请码不正确」；正确则注册为 `TEACHER` | 邀请码分支 |
| 学生不受邀请码限制 | 学生带任意邀请码 | 注册成功，角色仍为 `STUDENT` | 忽略邀请码 |
| 邀请码为空即关闭 | 配置为 `""`，尝试注册教师 | 抛「教师账号已关闭自助注册」 | 空串语义（对应缺陷 D5） |
| 角色缺省 | `role = null` | 注册为 `STUDENT` | `roleOrStudent()`（对应缺陷 P6） |

**设计说明**：这 13 个用例的顺序被刻意设计成「先失败先报」——例如「账号 3 位 + 口令 3 位」时，
应当报账号格式而不是口令长度。校验顺序在代码里是固定的（账号 → 姓名 → 口令 → 邀请码 → 重复），
测试逐条验证这个顺序，因为顺序错了用户会收到误导性的提示。

### 5.5 WorkflowIntegrationTest（8 例，集成）

**被测对象**：`AppContext` 装配出的全部服务 + 真实 JDBC DAO + 内存 H2。
**准备方式**：`@BeforeAll` 建库建表并灌入种子数据（教师、6 名学生、1 门课、1 个作业、4 份提交）。

| 用例 | 输入与操作 | 预期与断言 | 覆盖点 |
| --- | --- | --- | --- |
| 初始数据与登录 | 教师 `teacher / 123456`；错误口令 | 教师姓名「张明远」、`isTeacher()`；课程非空；错口令抛异常 | 种子数据 + 登录 |
| 建课并布置作业 | 建课 → 建作业（细则合计 100）→ 发布；再试图存合计 90 的细则 | 作业 id 非空、状态 `DRAFT`→`PUBLISHED`；非法权重抛异常；非法迁移抛异常 | 作业保存的事务性、状态机 |
| 学生提交 | 空内容、19 字、合法内容、再次更新 | 前两者抛异常；更新后内容为最新（不新增记录） | 字数边界 + 更新语义 |
| 分配互评 | 4 份提交，N = 2 | 任务数 = 提交数 × 2；作业状态变 `ALLOCATED`；重复分配需确认；学生只能看到自己的 2 条任务 | 分配 + 状态隐式迁移 + 盲评 |
| 打分与统计 | 评语 5 字（拒绝）、合法评语、重复提交 | 任务状态 `COMPLETED`；统计中该提交 `reviewCount = 1`、平均分 > 0；重复提交被拒 | 打分 → 计分 → 落库 → 统计 |
| 检索与导出 | 正则 `结构.*清晰`、非法正则 `[abc`、导出 CSV | 过滤结果 ≤ 全集；非法正则抛异常；CSV 以 BOM 开头且含「平均分」表头 | 正则 + CSV 编码 |
| 删除级联 | 删除作业 | 该作业的提交与任务计数为 0 | 级联清理顺序 |
| 自助注册 | 注册新账号 → 登录 → 重复注册 | 可登录；重复注册抛「已被注册」 | 注册链路与唯一约束 |

**设计说明**：集成测试与单元测试的分工是「单元测规则、集成测连接」。
例如「学生只能看到自己的任务」这条，只有在真实 SQL 下才有意义（`WHERE reviewer_id = ?`），
用内存 DAO 测不出来。反过来，「权重 90 该不该拒」属于规则，放在单元测试更快。

### 5.6 AiSuggestionProviderTest（11 例，协议）

**被测对象**：`DeepSeekSuggestionProvider` + `SuggestionParser` + `SuggestionPrompt`。
**测试替身**：`HttpServer` 本地桩，每个用例设置不同的响应（状态码、body、延迟）。

| 用例 | 输入与操作 | 预期与断言 | 覆盖点 |
| --- | --- | --- | --- |
| 标准响应 | 200 + 合法 JSON（3 个维度 + 总评） | `hints` 3 条，维度名与细则一致，`comment` 非空 | 解析主路径 |
| 请求体内容 | 同上，桩服务记录请求体 | body 含三个细则名、作业正文片段、`json_object` 标记 | 提示词与请求构造 |
| 越界分数 | 响应中给 999 / -20 / 4.3 | 裁剪为 10 / 0，4.3 对齐为 4.5 | `clamp` 与 0.5 对齐（缺陷 D3） |
| 编造维度 | 响应含「团队协作」（细则里没有） | 该条被丢弃，其余保留 | 维度白名单（缺陷 D4） |
| 噪声格式 | 维度名带「（40%）」后缀；整体被 ` ```json ` 包裹 | 仍能对齐到原维度，解析成功 | 清洗逻辑 |
| 非 JSON | 响应为一段纯文本 | 降级为「整段文字当总评」，不抛异常 | 降级分支 |
| 401 | 桩返回 401 | 抛 `AppException`，消息含「密钥」与 `ai.api.key` | 错误翻译 |
| 402 | 桩返回 402 | 消息含「余额」 | 错误翻译 |
| 超时 | 桩延迟超过客户端超时 | 消息含「超时」，不卡死 | 超时处理 |
| 未配置密钥 | `SuggestionProviders.fromConfig` 传入空 key | `isAvailable()` false，`suggest` 抛带原因的异常 | 空对象 |
| 配置关闭 | `ai.enabled=false` | 同上，原因为「已在配置中关闭」 | 装配分支 |

**设计说明**：这组测试的难点不是「解析对不对」，而是「模型不听话时系统怎么办」。
11 个用例里有 6 个在测异常路径，比例远高于其他测试类，原因就是这个模块的输入来自概率系统。

### 5.7 AppHomeTest（4 例，单元）

**被测对象**：`AppHome.root()` 与 `AppHome.resolve(path)`。
**背景**：这个类是为修复缺陷 P3（双击 jar 读到错误配置）而新增的，测试直接覆盖四种运行形态。

| 用例 | 输入与操作 | 预期与断言 | 覆盖点 |
| --- | --- | --- | --- |
| 定位项目根 | 正常运行时调用 `root()` | 返回的目录下存在 `pom.xml`；路径不以 `target` 结尾 | 从代码位置向上推导 |
| 相对/绝对路径解析 | `resolve("config/config.properties")`、`resolve("C:/tmp/x")` | 前者为 `root()` 下的绝对路径；后者原样返回 | 两种路径形态 |
| 系统属性优先 | 设置 `-Dpeerreview.home=/tmp/home` | `root()` 返回该目录 | 属性覆盖 |
| 属性为空白 | 设置 `-Dpeerreview.home=   ` | 忽略覆盖，仍按代码位置推导 | 空白处理 |

## 8 测试发现的真实缺陷

| 编号 | 缺陷 | 发现用例 | 修复方式 |
| --- | --- | --- | --- |
| D1 | 权重合计 90 时总分按 100 折算，结果偏低且无提示 | `ScoreCalculatorTest#normalizedStrategy` 的扩展用例 | 按实际权重合计归一 |
| D2 | 区间 min = max 时抛 `ArithmeticException` | `ScoreCalculatorTest#zeroSpanIsSafe` | `span <= 0` 返回 1.0 |
| D3 | 模型返回 4.3 分导致 `JSpinner` 显示与取值不一致 | `AiSuggestionProviderTest#clampsOutOfRangeScore` | 解析时对齐到 0.5 |
| D4 | 模型编造维度导致打分表多出空行 | `AiSuggestionProviderTest#dropsUnknownDimension` | 维度白名单过滤 |
| D5 | 邀请码配置为空串时教师注册仍未关闭 | `AuthServiceTest#teacherRegistrationDisabledWhenCodeBlank` | 改用 `getProperty` 直读，不走默认值回退 |

D2 与 D5 特别值得记录：前者是「数学边界」，只有把 min 与 max 设成相同才会触发，手工测试几乎不会想到；
后者是「配置语义」，`get(key, default)` 在空串时返回默认值，导致「关闭开关」永远关不掉。
两条都是**测试比人更耐心**的例子。

## 9 局限与改进

| 局限 | 影响 | 改进方案 |

## 10 附录：如何新增一个测试

以「给 `ReviewService` 增加一条『评语不得包含作者姓名』的规则」为例，步骤如下：

1. **判断层次**：这是业务规则，且需要真实 SQL 才能判断「作者是谁」，因此放在 `WorkflowIntegrationTest`；
2. **写失败用例**：先写断言「评语含作者姓名 → 抛 `ValidationException`」，此时测试应当失败；
3. **改实现**：在 `ReviewService.submit` 中，取到 `TaskRow` 后比较评语与作者姓名；
4. **跑全量**：`mvn test` 确认 50 + 1 全部通过，且没有破坏既有用例；
5. **补边界**：再补一条「评语含作者的**字**但不含完整姓名 → 允许通过」，避免规则过严；
6. **更新文档**：在本文档第 5.5 节的用例表中加一行，并说明覆盖点。

三条约定：

- 用例名用中文 `@DisplayName` 描述**行为**（「越界分数被裁剪」），不用 `test1`；
- 每个 `assertThrows` 都要断言消息内容，只断言异常类型会漏掉「提示写错」的问题；
- 涉及随机或时间的，一律注入种子或时钟，保证可复现。
